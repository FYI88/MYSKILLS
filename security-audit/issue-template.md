# Filing findings as issues (ask-matt triage flow)

After the report and `findings.json` are produced, file every CRITICAL and
WARNING as one issue; chains get one issue each at their end-state severity.
The issue body is an **agent brief** in the shape the `/triage` flow expects
(`ready-for-agent`), so a maintainer can run `/triage`, move the issue
through `needs-triage`, and an AFK agent can implement it from the brief
alone.

Rules:

1. **Category:** `bug` — the app behaves insecurely today. State role:
   `needs-triage` when filed.
2. **The disclaimer comes first.** Every issue body generated during this
   flow starts with the triage disclaimer line:
   `> *This was generated by AI during triage.*`
3. **Durable brief, evidence in its own section.** The contract sections
   (Current behavior / Desired behavior / Key interfaces / Acceptance
   criteria) describe **behavior and interfaces** — no file paths, no line
   numbers, they go stale. The precise `file:line` evidence lives in
   `findings.json` and in the brief's Evidence section only.
4. **Acceptance criteria are testable** and include the audit's own
   re-audit check (Phase 8): the finding's `status` in `findings.json`
   must flip to `resolved` on the follow-up run.
5. **One chain = one issue** at `end_severity`, listing its components —
   the components themselves do not get separate issues.

## Issue body template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** <finding.title>

**Current behavior:**
<finding.issue — what the app does today, in plain language, plus the
attack it enables. For chains: the composed attack path from component to
end state.>

**Desired behavior:**
<the secure behavior after the fix — including edge cases and error
conditions, e.g. "input longer than N characters is rejected, not
truncated into the sink">

**Key interfaces:**
- <the function/type/config the change lands on, described behaviorally —
  e.g. "the render helper used for user-supplied names must escape for the
  HTML context it lands in", "the merge function must never copy
  `__proto__` / `constructor` keys">
- <anything else the implementing agent should look for or change, by
  interface, not by file>

**Acceptance criteria:**
- [ ] <testable criterion 1>
- [ ] <testable criterion 2, including the re-audit: the follow-up
      security-audit run marks this finding resolved in findings.json>
- [ ] <regression check: behavior outside the fixed surface is unchanged>

**Out of scope:**
- <adjacent work that must not happen in this issue>

**Evidence:**
- File: <finding.file>:<finding.line>
- WSTG: <finding.wstg, comma-separated> · CWE: <finding.cwe>
- Section: <finding.section> · Verified: <finding.verified>
- PoC: <finding.poc>
- Suggested fix: <finding.fixed — or reference the fix pattern in
  fixes/, plus any caveats from the audit>
```

## Field mapping

| findings.json field | Template slot |
|---|---|
| `title` | Summary |
| `issue` | Current behavior |
| the secure behavior | Desired behavior |
| `file` / `line` | Evidence only (never in the contract sections) |
| `wstg` / `cwe` | Evidence |
| `poc` | Evidence |
| `fixed` / `why_works` | Evidence (Suggested fix) |
| `verified` | Evidence |
| `chain` / `chains[].components` | one issue per chain at `end_severity` |

## Re-audit loop (what makes a finding "resolved")

A later audit run reads the previous `findings.json` (Phase 8) and verifies
each `open` / `fix-proposed` finding against the current code — grep group
clean, dynamic pass shows no violation, behavior intact. Only then does the
finding's `status` become `resolved`. The issue's acceptance criteria
should say exactly that, so the implementer and the auditor agree on
"done."
